# 07 · 槽位分层迁移实施规划

06 篇评估确认了分层重构（底座 C 化 / 中间层协议 / 顶层保形）的方向与
两个设计前提。本文是落地规划：先以代码普查固定迁移面，再把 06 篇的四
阶段细化为可验收的步骤。规划遵循四条原则：

1. **已知缺陷延后。** 两处已确认的正确性缺陷（判型劫持、`__bases__`
   重赋值丢槽）以及其他已知与 CPython 的行为差异，一律推迟到架构迁移
   完成之后处理。迁移期间它们是基线的一部分，不是修复对象。
2. **行为冻结。** 已有类型的 R\* / 比较实现原样搬进新结构，即使其中
   混有已知的语义偏差。本迁移只换承载结构，不换语义——对齐是之后的事。
3. **试点验证。** 架构切换后先迁移个别类型验证新架构，不大面积铺开；
   试点暴露的问题修复完毕、经验沉淀后，才继续扩大范围。
4. **对齐日常化。** 架构稳定之后，CPython 对齐工作回归日常节奏处理，
   不做集中式冲刺。

## 一、迁移面普查

以下清单基于当前 master 的代码普查（`PyOperators` 全文、槽字段生成产物、
全部槽读点/写点 grep），是阶段划分的依据。

### 协议承载点（收进中间层的分发逻辑）

| 位置 | 承载的协议知识 |
| --- | --- |
| `PyOperators.ReflectiveOperator` | 三族共用入口：int-int 快路径、类型相同判定、右子类优先、同类型省略反射（算术族）、左先/右先两套配对取槽 |
| `PyOperators.EvalReflectiveOperator` | R\* 槽的参数位交换（`otherFunc(other, self)`） |
| `PyOperators` 两个 switch（12 处） | 比较镜像配对（Lt↔Gt、Le↔Ge） |
| `PyOperators.ApplySequenceFallback` | 数族落空后的序列族回退（sq_concat / sq_repeat，左序优先） |
| `PySpecialMethods.DivMod`（341-360） | 独立的简化版反射分发：左 `DivMod` → 右 `RDivMod` 交换 → TypeError，**无子类优先、无同类型省略**——与 CPython 的 `PyNumber_Divmod`（共用 `binary_op`）存在已知差异，按原则 1 冻结保留 |

### 槽读点（消费方）

普查结论非常有利：**除上述两个分发点外，比较六槽、就地槽与 R\* 槽
（`RDivMod` 一处除外）在代码库中没有任何直接读点**。`PyComparer`
（dict/set 键比较、`in`、`sorted` 的比较入口）全部经 `PyOperators`
转发，比较族收敛为单一 `richcmp` 对它们零影响。非运算槽（`Get`/
`GetItem`/`Len` 等）的直接读点（`PyReversedObject`、`PyBuiltinFunctions`
的 getattr 降级、`PyStrObject` 的 % 格式化探测等）不在迁移范围内。

### 槽写点（生产方）

| 时机 | 机制 | 迁移动作 |
| --- | --- | --- |
| 编译期内置 | `FillSlot` + Sealed 桥 + `FillReflectedSlots` 合成器 + `PyAttributes` wrapper | 适配视图接管，最终由拆层后的生成器接管 |
| MRO 合并 | `FillNullWith`（41 直字段 + 48 数字段 + 4 序列字段按引用拷贝） | 收敛后字段数减 20（14 R\* + 6 比较） |
| 运行期解析 | `TrySetSlot` / `ClearSlot` / `TrySetWrappedSlot`（堆类型字典 ↔ 槽，含 nb/sq 双族互斥与 wrapper 识别） | 对应 case 改写为中间层入口 |
| `__bases__` 变更 | `RebuildMro` / `ApplyBasesAssignment` | 已知缺陷区域，冻结不动 |

### 关键数字

- 槽字段：41 直接 + 48 数族（21 前向 / 14 反射 / 13 就地）+ 4 序列族；
  收敛目标为删除 14 个 R\* 与 6 个比较槽、新增 1 个 `RichCompare`。
- 手写运算覆写：约 64 个类型文件（最重的是 dict items 视图 21 处、
  float 15 处）。
- 生成器：`PyTypeGenerator` 产物 178 个类型文件；`InternalPyTypeObject
  Generator` 产物 4 个（`Slots` / `Virtual` / `Sealed` / `Partial`）；
  `Declarations` 清单按前向/反射/比较/就地四段组织。

### 两项对桥设计有决定性影响的现状事实

**Sealed 桥的守卫是 TypeError 而非 NotImplemented。**
`PyTypeObjectOfT.Sealed.g.cs` 中每个桥以 `self is not TObject` 直接报
`Runtime_Type_MethodReceiveSelfWrongType`。协议场景下这个报错会杀掉
回退链——现状靠合成器的前置守卫（`self is TObject ? … : NotImplemented`）
规避。中间层化后，桥的守卫必须按位置分流：前向位外类型 self 属协议
正常路径（返回 NotImplemented 让分发器继续），桥内部的自我一致性检查
仍可保留强报告。

**顶层反射虚方法的 self 位承诺是本类型，且已有成熟手写模式。**
float 的手写 R\* 展示了三种形态：可交换运算直接转发前向（`RAdd` →
`Add`）；不可交换运算手写翻转算术（`RSub` 里 `d - self.Value`）；其余
落 `base.RSub` 兜底。这些签名（`self: PyFloatObject`）与 Python 层
`__rsub__` 的 self 语义天然一致，迁移后可原样保留——印证了 06 篇
「类型安全与 Py 层外形一致」的论断。

## 二、阶段划分

06 篇的四阶段在本文原则下细化为五阶段。核心排序决策：**生成器拆层
放最后**。适配视图建在运行层（中间层读取旧槽产物并包装），阶段 1-3
完全不需要触碰生成器，每一步的 diff 面因此可控；中间层 API 经历试点
检验稳定后，阶段 4 才拆生成器，避免两层生成器跟着接口反复返工。

### 阶段 0：基线冻结

- 全量测试跑通并存档结果；把已知差异（两处 P1 缺陷、`DivMod` 简化、
  其他已记录的 R\* 行为偏差）逐条登记为「迁移期间保持原样」的基线条目。
- 选定试点类型组合并写下预期行为（见阶段 3）。
- 验收：基线文档评审通过，无代码变更。

### 阶段 1：中间层落地（纯新增，不接线）

- 新增中间层类型（暂名 `XXXTypeObject<T>`）：C 风格运算入口
  （`add` / `richcmp` / 就地族，self 为 `PyObject` 无类型承诺）、协议
  骨架（三步原序分发、结构判型、交换表、同槽省略）、槽函数工厂接口
  （字典驱动与虚方法驱动两种，共享骨架、各插桩翻找回调）。
- 适配视图：旧槽 → C 形态的包装（`add(left, right)` = 左前向直通 +
  右 R\* 交换调用；六比较槽 = op 分派）。`DivMod` 的简化协议按基线
  原样包进适配视图。
- 验收：新代码编译零警告进主干，行为零变化（未接线）。

### 阶段 2：分发器整体切换（一刀，行为保持）

- `PyOperators` 内部改走中间层，对外 API 与签名不变；int-int 快路径
  原样保留；序列回退逻辑随入口迁移。
- `PySpecialMethods.DivMod` 同步切换（适配视图保持其简化协议）。
- 验收：全量测试与阶段 0 基线**零 diff**（含已知差异的原样保持）；
  运算热路径基准不回归。单一提交，可整体 revert。

### 阶段 3：试点类型迁移（个别验证）

试点组合按「每类型验证一条新架构路径」选择：

| 试点 | 验证的路径 | 依据 |
| --- | --- | --- |
| frozenset | 静态 C 风格守卫路径（双侧类型检查 + NotImplemented 回退） | set 族是 CPython 静态槽的标准形态，PySharp 侧覆写面小（7 处） |
| bool | 继承敏感路径：槽 delegate 继承判定、经 MRO 捡拾基类反射 wrapper | `IsInheritedForwardSlot` 搬迁正确性的最小验证样本 |
| float | 桥的反射回退路径：手写 R\* 密集（6 个不可交换反射 + 兜底转发） | 对桥「非平凡转发」前提的最强压力测试 |

每个试点：删除该类型的适配视图依赖，改为本地 C 风格实现 / 新工厂桥；
配 CPython 3.14 对照回归（含子类化场景）。**试点暴露的问题在本阶段
修复完毕并沉淀经验后，才讨论扩大范围**；不做大面积迁移。

验收：三个试点全对照通过；桥与工厂的缺口清单关闭。

### 阶段 4：生成器拆层与旧物删除

- 中间层 API 冻结后，生成器拆为两层：底层生成「槽位 ↔ 中间层」的
  桥接与字典槽工厂；面向 `PyTypeObject<T>` 的生成器只对接中间层 API。
- 逐类型按试点模式扩大迁移（节奏由日常维护带宽决定，非冲刺）。
- 终态删除：R\* 槽字段、比较六槽、镜像硬编码、`FillReflectedSlots`
  槽字段级合成、`Declarations` 反射段、五张 switch 中对应 case。
- 验收：删除后全量绿；`PyTypeSlots` 字段数与 CPython 槽结构一一对应。

## 三、风险与对策

- **行为冻结期的测试盲区**：已知差异不修，容易在 review 中被「顺手
  修掉」从而污染行为保持性质。对策：基线条目挂在对应 PR 模板里，迁移
  PR 一律声明「不改语义」。
- **适配视图与旧分发的 subtle 分歧**：`DivMod` 的子类优先缺失这类差
  异必须原样包装而非「顺手补齐」——补齐属于阶段 4 之后的对齐工作。
- **中间层 API 反复**：阶段 1-3 期间 API 变更成本尚低（消费方少），
  阶段 4 冻结后变更要走 deprecation 流程。
- **回滚**：阶段 1 纯新增可静默回滚；阶段 2 单提交可 revert；阶段 3
  按类型粒度回滚；阶段 4 的删除以「旧物清单」为单位分批进行。
