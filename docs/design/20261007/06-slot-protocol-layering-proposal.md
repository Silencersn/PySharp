# 06 · 槽位分层重构提案评估

针对 02 篇确认的结构性问题，一项重构提案提出将类型体系按「语义/便利」
拆为三层。本文对该提案做独立评估：先转述提案，再论证其对症性与可行性，
指出两个需要在设计阶段补正的前提，最后给出分阶段实施路径。

## 提案转述

现状是 `PyTypeObject<T>` 单层同时承担两个角色：对扩展作者暴露类 Python
层外形的类型安全 API（虚方法覆写、独立反射与比较方法），对内建实现又
直接充当槽语义的载体。这个双重身份带来便利（类型安全、符合 Python 层
惯性），也带来系统性的成本——语义正确性与表达便利在同一层里互相挤压。

提案的回应是拆层：

| 层 | 形态 | 职责 |
| --- | --- | --- |
| 底座 `PyTypeSlots` | 对标 CPython C 层：只有前向槽（`Add`/`Sub`/…）与单一 `RichCompare(self, other, op)`，**无 R\* 反射槽字段、无六个独立比较槽** | 纯数据，不承载协议知识 |
| 中间层 `XXXTypeObject<T>` | C 风格运算 API：`add(PyObject, PyObject)`、`richcmp(PyObject, PyObject, int)`，self 无类型承诺 | 运算协议的全部边界语义：三步分发、子类优先、交换表、槽函数工厂 |
| 顶层 `PyTypeObject<T>` | 现有类型安全虚方法覆写 API 原样保留，内部桥接到中间层 C 风格入口 | 只负责类型安全与 Python 层惯性，面向扩展 |

配套两点：源生成器拆为两层（底层生成「槽位 ↔ 中间层」桥接，面向
`PyTypeObject<T>` 的生成器只对接中间层 API）；现有内建类型按需迁移。
预期效果是顶层「不必在语义正确性与表达便利之间取舍」——前者整体由
中间层负责。

## 对症性

提案直击 02 篇的三个结构性发现：

**知识收拢。** 现状中「方向/操作码」知识分散在三处：槽结构（R\* 字段
与六个比较字段的存在本身）、分发层（[PyOperators.cs](../../reference/internals/protocol-dispatch.md)
里 `EvalLeftFirst`/`EvalRightFirst` 的配对取槽与 12 处镜像硬编码）、
合成器（`FillReflectedSlots` 的守卫转发）。提案将其收拢到中间层一处，
形态与 CPython 一致：算术协议在 `binary_op1` + 槽函数，比较镜像退化为
`_Py_SwappedOp` 这样一张数据表。「摊开为结构知识」的维护税随之消失。

**第三步原序可表达。** `binary_op1` 第三步以 `w.slot(v, w)` 原序调用
右类型槽——self 位收到左操作数。现状的 sealed 桥（self 承诺是
`TObject`）写不出这个语义，只能靠 R\* 槽在分发层交换参数来侧向绕开，
这正是结构分叉的根源。中间层的 C 风格签名（self 为 `PyObject`）让
第三步成为一句直白的调用。

**守卫从约定变签名。** 反射合成的正确性依赖「前向槽对 other 有类型
守卫」这一未成文约定（set 幸免、dict 视图踩雷）。底座 C 化后，槽实现
的签名 `add(PyObject, PyObject)` 本身就不含 self 的类型承诺，守卫检查
成为实现者的必经语法而非隐含前提——CPython 静态槽（如 `set_sub` 双侧
`PyAnySet_Check`）正是这个形态。PR #567 式的点状补丁（手写 `RSub`）
不再有存在的场景。

对两个已确认缺陷的关系：判型劫持（05 篇 P1-1）的土壤被铲除——中间层
分发器对标 `binary_op1` 的 `PyType_IsSubtype` 结构判型，语义判型不再有
出现的位置；但该缺陷修复是一行 `ReferenceEquals` 的事，不必等重构。
`RebuildMro` 丢自有槽（P1-2）与槽形态无关，照原建议修。

## 需要补正的两个前提

提案方向成立，但有两处表述偏乐观，需在设计阶段补正，否则实现会走样。

### 前提一：顶层桥是协议承载者，不是平凡转发

「内部封装并转发」的表述只对了一半。考虑算术反射：顶层保留 R\* 虚方法
覆写（如 dict 视图手写的 `RSub`），其可达性要求——当左类型槽返回
NotImplemented 后，右类型的反射方法必须被尝试。若桥只是
`self is TObject t ? t.VirtualSub(other) : NotImplemented` 的纯转发，
则中间层第三步 `rightType.add(left, right)` 中 self（左操作数）不是
`TObject`，桥直接返回 NotImplemented，用户覆写的 R\* 永远不可达。

正确形态的桥是 `SLOT1BINFULL` 的面向对象等价物：前向守卫转发，加上
NotImplemented 后的反射回退（self 不是本类型时，检查 other 是否是
`TObject` 且覆写了对应 R\* 方法，是则调用）。这与 CPython 完全同构——
`slot_nb_add` 的反射协议也在槽函数体内而非分发器里。因此「中间层负责
语义」应精确化为：**协议骨架（三步顺序、子类判定、交换表、反射回退的
编排）由中间层提供并只写一份；槽函数（顶层桥与字典驱动的动态槽工厂）
复用该骨架，只插桩各自的「翻找」回调**——桥翻虚方法覆写表，堆类型工
厂翻类型字典。两者在分发器面前同构，均为「槽函数的提供者」。

顺带的推论：`IsInheritedForwardSlot` 的继承判定（bool 经 MRO 捡起 int
的 `__radd__`）不会消失，只是从构造期合成搬进桥的翻找逻辑；bool/int
这对案例应当随迁移带上回归测试。

### 前提二：分发器是单点，不能逐类型双轨

「按需迁移」对内建类型的槽实现成立，对分发器不成立：一次二元运算的
三步必须走同一套逻辑，不可能按左右类型的新旧选择分发器。因此迁移的
第一刀是分发器整体切换，旧槽形态以**适配视图**存活——中间层的
`add(left, right)` 读取旧槽时包装为「左前向槽直通 + 右 R\* 槽交换调
用」，比较族六个槽包装为 `richcmp` 的 op 分派。可以证明这与现行语义
行为等价（现行 `EvalReflectiveOperator` 本身就是参数位交换调用，适配
视图只是把交换下沉一格；同类型省略反射的差异场景——如 int/bool 共享
槽 delegate——由合成槽的 `self is TObject` 守卫吸收为 NotImplemented，
最终行为一致）。这也是本提案可行性的最强论据：**C 形态是更细的粒度，
Py 外形可以由 C 形态加知识合成，反之不行**——这正是 02 篇结构分叉
结论的另一面。

## 代价与风险

- **一次性工程量大。** 全量内建类型迁移、分发器重写、生成器拆两层。
  这笔成本换的是「知识从三处分散收拢为一处」的长期维护收益，属
  典型的搬迁式重构：旧债一次结清，但结清期间回归验证负担最重。
- **中间层上帝化风险。** 若把布局、注册、槽缓存同步也顺手收进中间层，
  会重出 `type.__new__` 巨型方法的问题。职责应严格限定为「协议分发 +
  槽函数工厂」；tp_dict 单一真理源、三层缓存一致性是独立议题，可顺带
  但非必须。
- **生成器接口要先稳。** 两层生成器都对接中间层 API，接口若在迁移期
  反复变动，两层生成器跟着反复改。中间层 API 应作为第一个交付物冻结。
- **性能中性偏正。** int-int 快路径保留；正常路径槽调用次数近似（反射
  步从 delegate 调用变为桥内判定）；槽结构缩小（R\* 12 槽 + 比较 6 槽
  收敛）利好 `FillNullWith` 与缓存行；构造期 13 次 `FillReflectedSlot`
  消失。双 NotImplemented 落 TypeError 的冷路径不受影响。
- **迁移期一致性验证。** 两套语义并存期间最怕 subtle 分歧，迁移第一刀
  （适配视图整体切换）应声明为行为保持重构，以 test_pyfiles 全量 +
  CPython 3.14 对照把关。

## 与既有建议的衔接

02 篇对反射合成给出三级建议（约定成文 / PYSPI 分析器 / 默认不合成）。
本提案相当于第四级——架构重构使合成器本身消失。落地后：槽字段级合成
与镜像表删除；字典 wrapper 级合成保留（Py 层属性可见性，对标
`wrap_binaryfunc_r`）；「守卫约定成文」仍然需要——它从「合成器的隐含
前提」变为「C 风格槽实现者的显式责任」，CPython 同样以此约定运转。
P1 两缺陷按原建议先行修复，不与重构绑定。

## 建议实施路径

1. **冻结中间层 API**（C 风格运算入口 + 协议骨架 + 槽函数工厂接口），
   附设计文档与 bool/int、dict 视图等已知边界案例的语义说明。
2. **行为保持切换**：新分发器（结构判型 + 三步原序 + 同槽省略）落地，
   旧槽经适配视图接入，全量测试通过后一夜切换。
3. **按需收敛**：内建类型逐个将适配视图换成本地 C 风格实现（守卫 +
   计算），`PyTypeObject<T>` 桥逐个切到新工厂；每类型迁移配对照回归。
4. **删除旧物**：R\* 槽字段、比较六槽、镜像硬编码、`FillReflectedSlots`
   槽字段级合成，及对应的生成器模板分支。

## 结论

提案是对 02 篇结构性结论的正解式回应：既然焊点麻烦的根源是外形与语义
在同一个抽象层打架，就把语义下沉为纯 C 形态底座、外形保留在纯便利顶
层、协议知识收拢进显式的中间层。方向正确、对症，可行性由「C 形态粒度
更细」保证。两个补正——桥须承载反射回退、分发器须整体切换——都是
设计补丁而非方向修正。建议按四阶段推进，P1 缺陷修复先行。
