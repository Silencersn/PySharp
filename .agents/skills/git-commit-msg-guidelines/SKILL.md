# Git Commit Message Guidelines

## 提交信息规范

提交说明的结构如下所示：

```
<type><scope>: <description>

<body>
```

### 提交类型 type

> 使用 _小写英文_，**必须** 从提供的选项中选择

包含以下选项：

1. **feat:** 用于在代码库中新增了一个功能；
2. **fix:** 用于代码库中修复了一个 bug；
3. **build:** 用于修改项目构建系统，例如修改依赖库、外部接口或者升级 .NET 版本等；
4. **chore:** 用于对非业务性代码进行修改，例如修改构建流程或者工具配置等；
5. **docs:** 用于修改文档，例如修改 README 文件、API 文档等；
6. **style:** 用于修改代码的样式，例如调整缩进、空格、空行等；
7. **refactor:** 用于重构代码，例如修改代码结构、变量名、函数名等对功能逻辑没有影响或影响较小；
8. **perf:** 用于优化性能，例如提升代码的性能、减少内存占用等；
9. **test:** 用于修改测试用例，例如添加、删除、修改代码的测试用例等。

<br/>

> 由于 PySharp 的项目性质，当一个提交的主要目的为 _对齐 CPython 行为_ 时，不应盲目的选择 `feat` 或 `fix` 作为提交类型。<br/>
> 若本次对齐的行为此前在 PySharp 中不存在，则为 `feat`（例如实现了此前没有的模块/函数、为某个函数添加了此前不支持的参数）。<br/>
> 若本次对齐的行为此前在 PySharp 中已存在，则为 `fix` （例如修复在校验参数时使用了错误的异常类型）。<br/>
> 不应把粒度划分过细，从而认为本次对齐的行为此前不存在，导致大量使用 `feat`。<br/>
> 不应盲目把 _对齐 CPython_ 当作 _修复偏差_，导致大量使用 `fix`。<br/>
> 不应以 _过往提交的选择_ 来为自己现在的选择背书。一是因为过往提交的选择可能本身是错误实践；二是因为过往使用的规范与当前不同，同一提交可能符合过往规范，但不满足本规范。<br/>
> 若对于部分提交使用以上规则后仍难以区分 `feat` 与 `fix` 的，可考虑以 _改动量_ 等其他参数作为判断依据，如改动量越大越倾向于 `feat`。


### 范围 scope

> 使用 _小写英文_，无固定选项，1 至 2 个单词，多个单词使用 `-` 连接

为提交类型添加一个围在圆括号内的范围，以为其提供额外的上下文信息。

推荐只使用 1 个单词。

### 描述

> 使用 _简体中文_，不超过 50 个字符

描述与前缀之间需使用 `: `（英文冒号 + 空格）进行连接。

描述以动词开头：如添加、实现、修复、删除、更新、将、使用、提取、调整、迁移、替换、新增、激活等。

描述需保持精炼、简洁、有针对性，不推荐 `对齐 CPython 3.14` 等显然与项目目标重合的冗余描述。

### 正文

> 使用 _简体中文_

正文与标题行之间需保留一行空白行。

每行正文必须以 `- ` 作为开头，不得超过 5 行（尽可能使用较少的行数），每行不得超过 50 个字符，每行必须单独成句。

正文需保持简洁和一定概括性，不得记录过于具体的内容（尤其是行号等）


## 提交内容获取

> 除非用户有额外的附加命令，否则只允许运行 `git status` 和 `git diff` 两类只读命令，不得擅自修改 Git 状态

1. 当用户有明确指定的范围时，只对用户指出的范围编写提交消息
2. 当用户未明确指定时：
   1. 若变更**全部**在暂存区或未暂存区，则直接为所有变更编写提交消息
   2. 若暂存区或未暂存区**均有**变更，则为暂存区变更编写提交消息，然后告知用户信息只包含暂存区而不含未暂存区
   3. 若暂存区或未暂存区**均无**变更，则不编写消息，然后告知用户无变更

## 提交信息展示

将完整的提交信息放在单个 `txt` 代码块内展示给用户
